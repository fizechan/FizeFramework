# 跨层思考指南

> **目的**：实现跨层功能前，先梳理各层之间的数据流。

---

## 问题所在

**大多数缺陷发生在层与层的交界处**，而非单一层内部。

常见的跨层缺陷包括：

- API 返回格式 A，前端却按格式 B 解析
- 数据库保存 X，服务转换为 Y 时丢失数据
- 多个层各自实现同一逻辑，行为却不一致

---

## 实现跨层功能前

### 第一步：梳理数据流

画出数据的流转路径：

```
来源 → 转换 → 存储 → 读取 → 转换 → 展示
```

对每一条数据流转，逐项确认：

- 数据的格式是什么？
- 哪些环节可能出错？
- 由哪一层负责校验？

### 第二步：识别边界

| 边界 | 常见问题 |
| -------- | ------------- |
| 入口 ↔ App::init | 漏传 `root_path`、Env 未就绪就读 Config |
| Config ↔ 组件 | 占位符未替换、空 `database` 仍去连库 |
| Url::parse ↔ Action 注入 | `$_GET` 副作用与 `Request::get` 不一致 |
| Controller ↔ Handler | 把 `HttpResponseException` 当故障 |
| App 单例 ↔ 测试 | 静态 `$module` / handler / OB 泄漏 |
| 后端 ↔ 前端 | 序列化格式、日期格式 |
| 组件 ↔ 组件 | Props 结构变化 |

### 第三步：定义契约

对每个边界明确：

- 输入的准确格式是什么？
- 输出的准确格式是什么？
- 可能出现哪些错误？

---

## 常见跨层错误

### 错误一：隐含假设数据格式

**不推荐**：未确认就假设日期格式

**推荐**：在边界处显式转换格式

### 错误二：校验逻辑散落在多层

**不推荐**：在多个层重复校验同一内容

**推荐**：在入口处统一校验

### 错误三：抽象泄漏

**不推荐**：组件直接依赖数据库结构

**推荐**：每一层只了解相邻层

### 错误四：每个调用方各自解析同一载荷

**不推荐**：命令读取 JSONL 事件时，在各处直接转换字段类型：

```typescript
const thread = (ev as { thread?: string }).thread;
const labels = (ev as { labels?: string[] }).labels;
```

这看似只是局部代码，实际却让每个调用方都各自维护一份事件契约。字段一旦变化，就容易只更新一个命令而遗漏其他命令。

**推荐**：在事件边界处统一解码，再提供有类型的投影：

```typescript
if (!isThreadEvent(ev)) return false;
return ev.thread === filter.thread;
```

**规则**：对于只追加日志、JSON 流、RPC 载荷或配置文件，应由一个明确的模块统一负责：

- 事件 / 载荷类型定义
- 类型守卫，以及从 `unknown` 到规范类型的转换
- UI 命令使用的元数据投影
- 从事实来源重放状态的 reducer

渲染代码可以格式化字段，但不能重新定义载荷契约。

## 跨层功能检查清单

实现前：

- [ ] 已梳理完整数据流
- [ ] 已识别所有层间边界
- [ ] 已定义每个边界的数据格式
- [ ] 已确定校验发生的位置

实现后：

- [ ] 已测试边界情况（null、空值、无效值）
- [ ] 已核实每个边界的错误处理
- [ ] 已检查数据往返后仍然完整
- [ ] 已确认调用方导入并使用共享解码器 / 投影，而不是在本地转换载荷字段
- [ ] 已确认派生状态可追溯到来源事件标识符（`seq`、`id`、`version`），没有另造一套游标

## 跨平台模板一致性

Trellis 的命令模板（例如 `record-session.md`）会在**多个平台**中以相同或近似的内容存在，这属于跨层边界。

### 修改命令模板后的检查清单

- [ ] 找出包含同一命令的所有平台：`find src/templates/*/commands/trellis/ -name "<command>.*"`
- [ ] 更新所有平台副本（Markdown `.md` 和 TOML `.toml`）
- [ ] 对 Gemini TOML 调整续行符（`\\` 与 `\`）及三引号字符串
- [ ] 运行 `/trellis:check-cross-layer`，确认没有遗漏

**实际案例**：Claude 平台的 `record-session.md` 改用 `--mode record` 后，遗漏了 iFlow、Kilo、OpenCode 和 Gemini 副本，最终由跨层检查发现。

---

## 生成式运行时模板的升级一致性

有些生成文件既是文档，也是运行时输入。在 Trellis 中，`get_context.py`、`workflow_phase.py`、`SessionStart` 过滤器和逐轮 hook 都会解析 `.trellis/workflow.md`。模板变更必须同时验证全新初始化和升级路径。

### 修改由运行时解析的模板后的检查清单

- [ ] 找出所有会读取该模板的运行时解析器，不要只检查负责安装模板的写入逻辑
- [ ] 检查相关语法是否位于标签块等显式托管区域之外
- [ ] 验证全新 `init` 的输出，以及将较旧版本写入 `.trellis/.version` 的 `update` 场景
- [ ] 使用未经修改的旧版模板夹具添加升级回归测试，并断言安装后的文件已更新为当前打包版本
- [ ] 更新负责该运行时契约的后端规范

---

## 版本化文档边界

版本化文档属于跨层边界：源文件路径、`docs.json` 中的版本路由和最终显示的版本选择器都必须指向同一发布线。

### 编辑版本化文档前的检查清单

- [ ] 确定目标发布线：stable、beta 或 RC
- [ ] 确认所编辑的 MDX 路径与发布线相符：
  - stable: `docs-site/{start,advanced,...}` and `docs-site/zh/{start,advanced,...}`
  - beta: `docs-site/beta/**` and `docs-site/zh/beta/**`
  - RC: `docs-site/rc/**` and `docs-site/zh/rc/**`
- [ ] 确认 `docs.json` 导航将版本标签指向相同路径
- [ ] 提交前在另一版本目录中搜索当前发布线专属词语
- [ ] 若 beta 内容出现在根发布路径下，应视为源文件路径错误，而非渲染错误

**实际案例**：一项仅适用于 beta 的任务流程变更记录了
`prd.md`、`design.md`、`implement.md`、任务创建确认和 Codex 模式横幅，却放在根目录的 `start/` 与 `advanced/` 路径下。结果是文档站在 Release 选择器下展示了 0.6 beta 行为。修复方式是恢复根目录中的正式发布文档，将 0.6 内容移到 `beta/` 和 `zh/beta/`，并添加针对根发布目录的 beta 标记搜索检查.

**实际案例**：Codex inline 模式将工作流平台标记从
`[Codex]` / `[Kilo, Antigravity, Windsurf]` 改为 `[codex-sub-agent]` /
`[codex-inline, Kilo, Antigravity, Windsurf]`。全新初始化结果正确，但
`trellis update` 只合并了 `[workflow-state:*]` 块，并保留了块外的旧标记。升级项目因此装上了新的 hook 脚本，却仍使用旧工作流路由，导致 `get_context.py --mode phase --platform codex` 可能返回空的 Phase 2.1 详情。

## 模式检测探测检查清单

当 CLI 通过探测远程资源来自动判断模式时（例如检查 `index.json` 是否存在，以选择 marketplace 或直接下载）：

### 实现前

- [ ] 所有会使用探测结果的代码路径都执行探测（交互模式、`-y`、各种 `--flag` 组合）
- [ ] 区分 404 与暂时性错误，不要都当成「未找到」
- [ ] 遇到暂时性错误时**中止或重试**，绝不能静默切换模式
- [ ] 上下文变化时（例如用户切换来源）**重置**共享状态（缓存、预取数据）
- [ ] **快捷路径**（例如 `--template` 跳过选择器）必须具备与探测路径同等的错误处理能力；检查下游函数是否又调用了捕获所有错误的封装

### 实现后

- [ ] 追踪探测结果到模式决策分支的所有路径，确认不会意外落入其他分支
- [ ] 测试外部格式契约（giget URI、原始 URL），或至少在代码注释中说明
- [ ] 读取元数据时必须取得完整响应或使用流式解析器；绝不能把定长前缀当作完整 JSON 解析
- [ ] 用解析结果重建复合标识符时，确认**所有字段均被包含且位置正确**（例如 `provider:repo/path#ref`，而非 `provider:repo#ref/path`）
- [ ] 确认快捷路径调用的**操作函数**内部没有继续使用旧的「捕获所有错误」请求方式；需要区分错误时，必须使用能达到探测路径错误处理精度的变体

**实际案例**：自定义 registry 流程在 3 轮审查中发现 8 个缺陷，包括：探测仅在交互模式执行；暂时性错误落入错误模式；giget URI 中 `#ref` 位置错误；预取模板在切换来源后泄漏；`--template` 快捷路径跳过探测，但 `downloadTemplateById` 内部仍调用捕获所有错误的 `fetchTemplateIndex`，把超时误报为「模板未找到」。

**实际案例**：Agent 会话更新提示使用 `response.read(4096)` 获取 npm `latest` 元数据，并将结果当作完整 JSON 解析。`@mindfoldhq/trellis` 的包元数据超过 4 KB，导致 JSON 被截断、解析静默失败，首次注入会话时没有显示更新提示。修复方式是先读取完整响应再解析，并添加回归测试，在 `version` 字段后附加 8 KB 元数据尾部。

## 何时编写流程文档

遇到以下情况时，应编写详细的流程文档：

- 功能涉及 3 个或更多层
- 多个团队共同参与
- 数据格式较复杂
- 该功能过去曾引发缺陷

---

## 事件日志 / 投影边界

只追加日志是跨层契约。单个事件会经过以下流程：

```
CLI 输入 → 事件写入器 → events.jsonl → 读取器 → 过滤器 → reducer → 展示
```

### 新增事件类型或字段后的检查清单

- [ ] 将事件类型加入中央事件分类表
- [ ] 在事件层新增具类型的事件变体或类型守卫
- [ ] 为来自用户输入或 JSON 的数组 / 对象字段添加规范化辅助函数
- [ ] 仅由事件写入方负责分配 `seq` / `id`
- [ ] 过滤器和 reducer 使用具类型事件守卫，不要在本地转换字段
- [ ] 展示代码使用 reducer 输出或具类型事件，不要直接读取原始 JSON
- [ ] 至少添加一项回归测试，证明历史重放和实时过滤使用相同的过滤模型

**实际案例**：Thread channel 新增了 `kind: "thread"`、`description`、
`context`、标签和 `lastSeq`。最初的实现可以正确重放线程状态，但多个命令仍通过本地类型转换重新解析事件载荷字段。修复方式是由核心事件层统一维护 `ThreadChannelEvent` 和 `isThreadEvent`，由 `reduceChannelMetadata` 作为唯一的频道元数据投影，并由 `reduceThreads` 作为唯一的线程重放 reducer。
